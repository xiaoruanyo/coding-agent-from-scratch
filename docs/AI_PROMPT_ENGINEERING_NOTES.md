# AI 编程提示词与 Agent 工程协作 · 详细学习笔记

> 版本：V1（2026-11-03）。**这是一份系统学习笔记及后续课程提纲，不代表所有主题均已实践完成。**
>
> 定位：与仓库根目录 `CHEATSHEET.md` 分工。速查表只记核心术语和 API；本笔记保留**为什么、怎么提问、正反例、如何验收、什么时候升级为 Rule / Skill / Harness**。
>
> 课程主线：**Agent 架构 → Harness 工程 → AI 编程提示词工程与评测**。React/FastAPI 只用于把机制做成可见产品；**不以 Hermes Agent 或任何单一框架作为必修主线**。

## 1. 为什么要系统学习 AI 编程提示词？

在 AI 辅助编程中，使用者不必事先知道该用哪个 React Hook、哪个 Pydantic Validator，但必须能够说清：

- **结果**：功能完成后，使用者实际能够做什么？
- **边界**：哪些行为必须保持，哪些操作不能擅自做？
- **证据**：怎样证明修改生效、旧功能没有被破坏？
- **授权**：什么操作可以自主执行，哪些必须征求批准？

目标不是写出最长的提示词，而是让不必要的说明沉淀到项目规则，让每次任务更清晰、验证更可靠。

**核心原则**：业务目标由人定义；实现细节通常由 Agent 通过项目探索决定；测试与工具执行结果要可核验。

## 2. 四层指令模型：不要把所有要求塞进一条 Prompt

| 层 | 典型载体 | 负责什么 | 不应该做什么 |
| --- | --- | --- | --- |
| 单次任务 | Trae/Codex 用户消息 | 本次目标、特殊约束、验收口径 | 每次重复一整套通用规则 |
| 项目规则 | 项目规则文件 / AGENTS.md 等，依工具实际支持情况 | 项目结构、已有架构、不可破坏约定 | 规定所有功能必须用固定技术写法 |
| 可复用 Skill | 有触发条件、步骤、参考资料的工作方法 | 重复出现、经实践验证的专门流程 | 无验证地把一次性任务写成 Skill |
| Harness 硬约束 | 工具权限、路径校验、审批、测试 Runner | 必须可靠执行的安全/状态边界 | 假设 Prompt 会百分百阻止危险操作 |

**关键区分**：Prompt 可以要求“不要写出工作区”，但**真正限制路径访问**必须在工具代码或执行环境实现。Prompt 不是权限系统。

### 已实战的例子

Mini Coding Agent 的任务历史筛选：单次 Prompt 描述“增加按状态筛选，不影响点击详情和审批”，AI 自行选择 React State、派生数据和 CSS；验收时检查真实 Diff、构建和浏览器交互。

FastAPI 空白描述修复：单次 Prompt 描述“纯空白应返回 422，正常输入仍可创建”，AI 自行选择 Pydantic `field_validator`；验收时先复现、再跑回归测试。

## 3. 可复用的任务契约（Task Contract）

建议按复杂度选用，而不是强制每次填满。

### 简单任务：一句话 + 关键边界

> 给 Mini Coding Agent 任务历史增加状态筛选，保持当前布局，不能影响任务详情和审批；实现后运行相关检查并报告实际结果。

**为什么够用？** 目标和可观察行为清楚；技术实现可从仓库探索得出；通用工程纪律已由项目/全局规则承担。

### 中等任务：目标 → 范围 → 验收 → 权限

```text
目标：网页输入编程任务，点击「AI 分析」，显示真实 DeepSeek 返回的中文内容。
现有条件：后端已存在 POST /api/llm/analyze；保留「开始任务」演示功能。
边界：只修改相关前端；密钥不能进入浏览器；错误与加载状态必须可见。
验收：构建通过；空输入不发请求；成功、失败场景能在浏览器验证。
权限：可以自主阅读和修改相关代码、运行本地测试；不要发布或产生未经确认的收费调用。
交付：列出改动、实际测试、未验证部分及关键设计原因。
```

### 复杂任务：先分析方案再实施（必要时）

适用于影响数据模型、持久化、线程恢复、生产环境或多模块契约的事项：

```text
先检查现有架构和相关调用链，给出 2 个可行方案及其代价。
说明状态一致性、持久化、恢复、兼容性和风险差异。
本轮只分析，不修改代码；我决定方案后再授权实施。
```

**什么时候需要问用户？** 当不同合理选择会带来明显不同的产品行为、权限、成本或不可逆后果。普通变量名、Hook、文件拆分等技术细节无需频繁追问。

## 4. 三类开发提示词与审查重点

### A. 功能开发型

目标：实现新行为。示例：

> 在现有任务页面增加 AI 分析区域，调用既有 API，显示加载、成功和失败状态。保留旧任务创建流程。完成后验证。

审查：新增行为是否实际可见？有没有改动无关后端？有没有运行真正测试？是否把 Mock 结果误称真实 LLM 输出？

### B. Bug 修复型

目标：解释并解决异常。示例：

> `POST /api/tasks` 接受纯空白 instruction 并创建空任务。先复现，再定位根因，修复后补充 422 回归测试，保证正常创建和长度边界不退化。

审查顺序：**复现证据 → 根因假设 → 最小修复 → 针对性测试 → 邻近回归**。不能靠删断言、关闭检查或隐藏报错制造“成功”。

### C. 架构讨论型

目标：先判断设计取舍。示例：

> 希望 Agent 任务在后端重启后能继续。请解释当前 FastAPI、Runner、LangGraph、Checkpoint、事件存储的职责，比较可选方案和风险。本轮只分析，不写代码。

审查：是否区分事实、假设与方案？有没有过度设计？有没有讨论失败恢复、幂等、副作用和执行边界？

## 5. 工程化 Prompt 的进阶主题（后续将分课详细学习）

### 5.1 探索项目：检索优先、按需读取

不应把仓库所有文件一次性灌进上下文。典型路线：

`README / 目录 → 相关入口与调用方 → 定向搜索 → 局部读取 → 验证具体假设`

高质量指令示例：

> 请先定位相关路由、类型、调用方和测试；优先局部读取。解释你依据哪些文件得出结论。不确定时不要猜测不存在的 API。

### 5.2 Plan 和执行之间的边界

- 简单、低风险且目标明确：直接完成；不用“一小步就问一次”。
- 多模块或状态语义复杂：先给简短计划，持续根据证据调整。
- 涉及生产、重要数据删除、破坏性 Git、发布、收费资源：必须有匹配的明确授权。
- 用户要求“仅评审”：不得顺便修改代码。

### 5.3 上下文工程比长提示词更重要

模型真正看到的是被组织后的上下文，而不是仓库全部事实。学习重点：

- 如何选择与本轮问题相关的代码、日志、模型消息；
- 如何把任务目标、已确认事实、待验证问题分开记录；
- 如何在上下文压缩后保留重要约束，减少过期信息；
- 如何防止日志、网页、仓库代码中的恶意文字越权成为指令。

### 5.4 输出质量与证据分级

`AI 声称完成` ≠ `已提交改动` ≠ `构建通过` ≠ `功能真实验收`。

建议交付至少说明：

1. 用户能观察到的改变；
2. 实际修改文件及关键逻辑；
3. **实际执行过的**测试、命令、浏览器操作及结果；
4. 未验证项、已有异常与下一步建议。

用 Git Diff 审查是否存在无关重构、危险写入、未授权改动和测试造假。

### 5.5 Rule、Skill 和 Harness 该怎么选？

遇到一个新问题时依次判断：

- **本轮特例** → 放单次 Prompt；
- **所有项目都适用的协作纪律** → 放全局规则；
- **只对本仓库成立的事实** → 放项目规则；
- **重复出现、步骤稳定、已被验证的专门工作流** → 候选 Skill；
- **必须在每次执行时强制成立的边界** → 用 Tool / Harness 实现。

避免把同一约束复制到五个地方；规则越多并不必然让 Agent 越可靠。

### 5.6 提示词如何评测与迭代？

先定义小型任务集，而不是凭一两次顺利输出就断定提示词质量高。

| 任务 | 验收证据 | 失败迹象 |
| --- | --- | --- |
| 前端筛选 | 切换状态、计数、恢复全部、浏览器验证 | 覆盖原历史数组、旧详情失效 |
| API 修复 | 纯空白 422、正常 201、回归测试 | 只改表单不守住后端边界 |
| LLM 分析 | 真正的 API 响应，模型声明未读代码 | 用 Mock 冒充真实推理 |
| 工具读取 | 真实 ToolMessage，路径/大小限制 | 只出现 tool_calls 就声称已读取 |

迭代方式：记录失败样例 → 定位是需求歧义、工具能力不足、上下文缺失还是执行边界失效 → 只修改相关 Prompt / Rule / Tool → 用原失败样例复测。

## 6. Harness 工程：从会调用 Tool 到可靠交付（课程主线，待逐课实践）

### 6.1 Harness 是什么，为什么不能等同于 Prompt？

我们把 **Harness（Agent 运行与工程约束层）** 定义为：围绕 LLM 的调用、工具执行、上下文构建、状态与会话管理、权限校验、执行控制、可观测性和结果验证等的一组工程机制。

它不必是某个开源项目，更不等同于 Hermes Agent；也不是简单多加几个 System Prompt。

```text
用户任务 / 任务契约
    ↓
Context Builder：选择规则、历史、代码与必要事实
    ↓
LLM：推理，提出工具调用或回答
    ↓
Tool Router / Policy：校验 schema、权限、依赖和副作用
    ↓
Tool Runner：在硬边界内真正执行，产出可核验的结果
    ↓
State / Event / Checkpoint：记录事实和可恢复现场
    ↓
Guard / Scheduler：检查是否可以继续、重试、审批或结束
    ↺ 视实际结果进入下一轮 LLM
    ↓
真实测试、交付报告、可观测与评测
```

这只是**教学职责图**，并非规定必须有上述名称的类、服务或固定执行顺序。实现可以是简单的 Python 程序，也可以基于 LangGraph 或其他运行时。

### 6.2 Harness 需要学习的六组核心机制

| 机制 | 核心问题 | 在当前 Mini Coding Agent 的具体落点 |
| --- | --- | --- |
| Loop / Runtime / 调度 | 谁发起下一轮、何时停止、怎样限制步数？ | LLM → Tool → LLM；终止条件、次数/时限 |
| Tool Policy / Sandbox | 模型请求能否直接执行？如何保护文件与命令？ | workspace、路径边界、只读/高风险工具审批 |
| Context Engineering | 哪些代码、消息、规则和事实应放进本轮模型上下文？ | 搜索 → 局部读取 → Working Summary；防过期信息 |
| State / Event / Persistence | 事实、UI 事件、Checkpoint 和 Memory 各是什么？ | 工具结果同步 State、SSE 展示、恢复线程 |
| Reliability / Recovery | 失败重试、策略回退、重复副作用和部分失败怎么处理？ | Retry/Loop/Recovery、幂等审批、Completion Guard |
| Observability / Evals | 怎样知道 Agent 真正更好，而非只会写漂亮总结？ | Tool Call 轨迹、文件 Diff、pytest、费用、回归任务集 |

### 6.3 把三个职责区分开

- **LLM**：选择行动和提出意图，不直接构成文件已修改、测试已通过的证据。
- **Workflow / LangGraph**：编排节点与状态更新；它可以是 Harness 的核心执行骨架之一，但本身不是完整 Harness。
- **Harness**：补上工具硬边界、上下文选择、执行与观测、审批、恢复、评测等工程约束；可以集成在相同进程，不代表一定要另起一个系统。

**举例**：模型输出“测试已经通过”，只有实际 pytest 工具的结果与对应代码版本能够支持成功结论。Prompt 写得再好也不能替代这条 Guard。

### 6.4 由简单到复杂的动手课程（每步必须可观察）

1. **工具消息链路**：模型真实提出 `tool_calls`，程序执行受限 `read_file`，产生对应 `ToolMessage`；网页展示请求与实际读取的区别。
2. **LangGraph Loop**：用 `StateGraph`、`ToolNode`、条件路由管理多轮；前端展示步骤，限制最大次数。
3. **Tool Policy**：加入路径边界、只读/写入分级与高风险审批；通过故意越界的测试证明拒绝生效。
4. **Context Builder**：对比全量读取与定向检索，记录相关性、上下文长度、成本和失误。
5. **State / Event / Checkpoint**：验证断开浏览器与重启后端分别会丢失哪些信息；设计受控恢复和幂等执行。
6. **完成条件与回归**：让模型在“没有成功测试”时声称完成，验证 Completion Guard 能阻断假成功。
7. **评测与迭代**：固定几个小型任务，比较 Prompt、工具策略、上下文和模型配置变化对成功率、成本、安全性及延迟的影响。

每个专题都包含：**为什么需要 → 最小反例 → 机制解释 → Trae 实现 → 在产品中观察 → 失败案例 → 验收证据 → 更新学习笔记**。

### 6.5 什么时候研究成熟 Harness 项目？

在我们能独立解释并验证上述核心机制后，再从开放项目中选一个或多个作为**工程对照案例**，评估真实的工具策略、上下文压缩、记忆、权限、执行环境与插件化设计。

比较的重点是**设计取舍与可扩展性**，不是预先宣布某个框架绝对最好。需要时可以研究 Claude Code、Codex、Hermes Agent 或其他项目，但都不是课程的固定毕业目标。

### 6.6 向数仓工作迁移的落地顺序

优先构建受控、只读的数仓工程助手：查询脱敏元数据、阅读 SQL、解释 SelectDB EXPLAIN、整理诊断证据；禁止未经授权的生产写入和不受控命令。通过可复用评测样例验证效果后，再考虑 Skill、MCP 和更高权限操作。

## 7. 产品可视化驱动的课程安排（更新）

| 阶段 | 核心学习 | 在 Mini Coding Agent 中观察到的成果 |
| --- | --- | --- |
| 当前阶段（已实战） | Trae 工程规则、提示词基础、React 筛选、Pydantic、HTTP/SSE、LangChain 调用 | 网页任务筛选 + 独立 AI 分析区，真实 DeepSeek 接口曾验证成功 |
| 下一阶段 A | Agent Loop、Tool Calling 消息协议、受控读取与上下文 | 网页展示模型实际读取的文件、工具调用及对应结果 |
| 下一阶段 B | LangGraph State、路由、Reducer、Checkpoint、审批 | 网页展示多步执行、暂停审批与恢复 |
| 下一阶段 C | Tool/Harness 安全边界、测试和有限重试 | 能从受控教学代码生成 Diff、审批修改并运行真实 pytest |
| 并行的 Harness 工程专题 | 工具策略、上下文、权限、状态、恢复、可观测性和评测 | 给自建 Agent 加入真实的 Guard、证据和诊断视图，并与成熟实现对比 |
| 进阶实践 | 针对工作流程打磨 Prompt、Rule、Skills 和评测样例 | 形成可复用的 SelectDB 慢 SQL 分析工作流 |

**前后端只讲必要知识**：用 Trae 完成 UI/接口，老师重点解释架构职责、模型行为、工具安全、验证证据；不为了学习框架而不断增加无关页面。
