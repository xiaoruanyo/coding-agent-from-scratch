# Mini Coding Agent：最终产品需求与版本边界

> 本文不是“今天已经完成的功能列表”，而是**整本教材最终必须交付的产品契约**。实现进度另见 [课程总导航](INDEX.md)。我们用它反推课程，而不是先学习任意多 API 再临时拼项目。

## 1. 一句话产品定义

一个**本地优先、单用户、针对已授权代码工作区**的小型 AI 编程助手。

用户可以在浏览器里输入修复任务，Agent 自动搜索与阅读代码、提出变更，写入前展示 Diff 并暂停等待批准，批准后执行经过权限限制的文件修改和真实测试，最终给出包含依据的结果报告。

这不是浏览器里的聊天机器人皮肤；它必须有对真实环境的可验证操作。

## 2. 一次端到端演示

准备一个有故意 Bug 和 pytest 用例的临时 Python 项目：

```text
demo-project/
├── calculator.py
└── test_calculator.py
```

用户在 UI 选择已配置的受控工作区，然后输入：

> 请修复 calculate_total 计算错误，修改前让我确认，完成后运行测试。

**期望的用户体验**：

1. 页面产生一个任务记录，显示当前工作区和时间；
2. Agent 读取或搜索相关文件，界面显示真实工具调用、目标文件和执行结果摘要；
3. Agent 发现代码问题并提出具体修改；程序生成可比对的旧代码与新代码；
4. 界面进入“等待批准”，展示本次具体 Diff；用户可以批准或拒绝；
5. 如果用户拒绝，本次修改必须没有副作用，Agent 能重新分析或者按明确取消请求结束；
6. 如果批准，程序只执行已获准的**相同**修改，不允许模型在审批后偷偷替换目标文件或参数；
7. 执行工具报告真实成功或失败；
8. 运行 pytest，UI 区分 PASS、FAIL、TIMEOUT、ERROR；
9. 普通 FAIL 可以分析并尝试修复，但不能无限循环；达到 V1 约定的次数限制后停止；
10. 完成时给出结构化状态（成功、失败、未验证或取消）、实际改动、真实测试结果和未完成事项。

## 3. V1 必须具备的页面

### 工作区与任务输入

- 显示当前操作的项目目录与安全提示；
- 输入任务描述，并能看到任务 ID 与状态；
- 显示最近任务记录，支持返回某一次历史任务；
- 对可能产生费用的外部模型调用明确告知。

### 任务执行时间线

每个关键步骤都有可追踪的事件：

```text
开始任务 → 模型分析 → search_code → read_file → 准备修改
→ 等待审批 → 修改执行 → 运行测试 → 更新事实 → 最终报告
```

时间线要区分：

- “模型请求调用”与“工具实际执行”；
- “审批等待”与“审批拒绝”；
- “已发起测试”与“测试真实完成”；
- “任务结束”与“任务验证成功”。

### 修改审批

- 文件路径和修改内容可见；
- 至少有逐行旧/新内容对比的 Diff；
- 明确按钮：批准／拒绝；
- 不允许通过刷新或重放请求绕过审批；
- 已拒绝的请求不得执行。

### 测试状态与最终报告

- 测试退出码、摘要、失败类别；
- 输出有合理截断且允许按需查看详情；
- 普通测试 FAIL 与 timeout 明确区分；
- 任何成功的代码修改会使之前的“已验证”状态失效；
- 不允许模型凭主观文本把状态改为通过。

## 4. V1 Agent Core 的能力范围

工具的起点：

```text
list_directory
list_symbols（Python AST 版即可）
search_code
read_file（限行）
replace_text（精确唯一匹配）
write_file（新建文件，不无条件覆盖）
run_test（固定受限 pytest）
```

**不提供**：

- 没有限制的通用 Shell；
- 任意系统路径读取；
- 静默删除整个目录；
- 自动推送到远程 Git；
- 生产服务器操作；
- 复杂自主联网能力。

这些功能不是“不够酷”，而是会大幅改变授权和隔离边界。需要时放进单独的进阶设计。

## 5. V1 的可靠性约束

### 权限

模型的输入与输出都视为不可信请求。文件写入的审批应绑定工具名、规范路径和准确修改内容；审批通过不代表允许越过工具的路径与资源限制。

### 执行

- 独立只读调用可以并行；有依赖的调用必须确定先后顺序。
- 一次 AIMessage 多个 Tool Calls，必须维护 tool_call_id 到结果的完整关联。
- 整批有高风险写入时，初版采用“批量暂停审批”；拒绝则全批不执行，并明确生成未执行结果。
- 工具失败后，对依赖其成功的后续工具产生“跳过”结果，不能伪造成功。
- 中断恢复与重试必须考虑写入副作用的重复执行。

### 验证

- 最多三次普通测试失败后终止自动修复，这是 V1 的约定；timeout/环境错误独立分类。
- “测试曾经通过”不是永久凭证。再次修改后应重新验证。
- 只要没有可核验的通过结果，最终不得宣称任务成功。

### 上下文

- 搜索返回结果数、读取行数与测试输出均有上限；
- 长任务进行 Working Summary，但摘要不代替权限与精确事实；
- 代码可被其他进程修改，需要时重新读取真实工作区。

## 6. 为了保持产品小体量，明确暂不做

第一版不做登录注册、团队权限系统、多用户并发远程执行、云端存储、大规模向量索引、Git 自动提交、多 Agent 协作和容器集群管理。先把本地单用户闭环做到可信。

**本地优先并不意味着本机进程自然安全。** 执行测试代码仍可能触发恶意副作用，因此第一版只能用于可信的、你自己控制的练习工作区。后续扩展篇会加入更完整的隔离和信任模型。

## 7. 功能验收不是“界面能点”

看 [验收标准](DEFINITION-OF-DONE.md)：每条能力必须拥有至少一个能够重复执行的验收过程。尤其是“用户拒绝写入后文件内容完全没变”“测试超时不得被报告为普通 FAIL”“模型说成功但没有真实测试时 UI 不显示通过”。

## 8. 技术栈与模块职责

| 模块 | 推荐技术 | 主要职责 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 任务输入、事件时间线、审批 Diff、测试与报告 |
| 后端 | Python + FastAPI | HTTP、任务/会话管理、事件流与审批恢复 |
| Agent Core | LangGraph + 最小 LangChain | 模型调用、图调度、状态、可靠路由 |
| 文件与测试 | pathlib / AST / pytest subprocess | 受控代码探索、修改、验证 |
| 检查点 | 开发阶段 InMemorySaver；后期持久化 saver | 暂停与恢复任务 |
| 测试 | pytest + 前端组件/端到端测试 | 证明真实行为而不是“看起来成功” |

产品界面、API 与 Graph 必须同一套状态语义；不能前端展示一个模型猜的成功，而后端仍记录 FAIL。
