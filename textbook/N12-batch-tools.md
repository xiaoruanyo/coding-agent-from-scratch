# N12｜一次 AIMessage 有多个 Tool Calls：整批审批、失败停止、并行与消息配对

> 本课把最近的四个架构决策放在同一张执行图里：**整批审批、拒绝后记录未执行、依赖调用失败时停止、独立只读调用允许并行**。这已经是一个简化 Harness 的设计题，不是 ToolNode 的简单 API 练习。

## 1. 为什么多个 Tool Calls 使问题变复杂？

假设模型一次提出：

```python
tool_calls = [
    {"name": "read_file", "args": {"path": "config.py"}, "id": "call_1"},
    {
        "name": "replace_text",
        "args": {
            "path": "main.py",
            "old_text": "return a - b",
            "new_text": "return a + b",
        },
        "id": "call_2",
    },
    {"name": "run_test", "args": {}, "id": "call_3"},
]
```

三个调用不是等价的：

- `read_file`：读取现有文件；
- `replace_text`：修改真实文件，产生副作用；
- `run_test`：验证当前代码，可能依赖修改已成功。

你不能简单把它们视为“一批可以任意并行的函数”。

如果只靠 `ToolNode(tools)`，并不能自动得到我们想要的所有审批、依赖和失败处理保证。

## 2. 两种审批策略

### 方案 A：整批审批

只要这批包含需要审批的写操作，整批先暂停：

```text
AIMessage: [read_file, replace_text, run_test]
                    ↓
              approval_gate
                    ↓
            存在高风险 Tool？
                /         \
              否           是
              ↓            ↓
            tools       interrupt
                           ↓
                          人工
                       /       \
                     批准      拒绝
                      ↓         ↓
                    tools     全批不执行
```

这是我们 V1 选择的方案：**牺牲一些效率，减少拆批的执行状态复杂度**。

### 方案 B：分别审批/分别执行

只读部分可先跑，写操作等审批。这更灵活，但会带来：

- 哪些工具已经完成、哪些仍等待；
- 只读结果是否在写入后过期；
- 部分执行成功、部分拒绝怎么反馈；
- ToolMessage 的对应关系；
- 依赖 Tool 如何停住。

V1 不追求这些高级能力。

## 3. 整批审批通过，不等于“整批以后随意执行”

用户批准的是显示出来的具体批次。

不能先给人看三个调用，批准后又让模型重新生成新的三个调用再执行。

待执行的工具名、ID、参数与相关 Diff 应固定，并在执行前验证。

此外，审批通过**不等于保证执行一定成功**。例如 `replace_text` 仍可能因为旧文本匹配不到而失败。

## 4. 拒绝一整批时，要给每个调用一个结果

假设用户拒绝了包含 `replace_text` 的这一批：

```text
call_1 → read_file   ：未执行
call_2 → replace_text：未执行，审批拒绝
call_3 → run_test    ：未执行
```

为了保持调用关系，生成三个对应的 ToolMessage：

```python
from langchain_core.messages import ToolMessage

results = [
    ToolMessage(
        tool_call_id="call_1",
        content="未执行：整批审批被拒绝。",
    ),
    ToolMessage(
        tool_call_id="call_2",
        content="未执行：用户拒绝本次文件修改。",
    ),
    ToolMessage(
        tool_call_id="call_3",
        content="未执行：整批审批被拒绝。",
    ),
]
```

这里的信息含义非常明确：

- 没有读取 `config.py`；
- 没有修改 `main.py`；
- 没有运行 pytest；
- 模型不能把“未执行”解释成“执行成功”。

**与每个 tool_call_id 对应的未执行结果**能让下一次 LLM 调用拿到完整的工具调用消息结构。

## 5. 如果审批通过，但第二个 Tool 失败呢？

假设：

```text
read_file(config.py)      → 成功
replace_text(main.py)     → 失败：旧文本不存在
run_test()                → 尚未执行
```

在我们的 V1 中，`run_test` 是为了验证前面的代码修改。因此修改失败后，**应停止这个有依赖的串行计划**，不要在“修改成功”的假设下继续。

结果：

```text
call_1 → 成功，真实读取结果
call_2 → 失败，真实错误
call_3 → 跳过，因为前置修改失败
```

注意“跳过”也要生成对应的 ToolMessage。

你不应该只返回：

```text
ToolMessage(call_2, "失败")
```

而丢掉 call_1 的实际读取结果和 call_3 的未执行状态。

## 6. “停止剩余调用”适用范围是什么？

这是非常值得掌握的限制：

**不是任何工具失败都应该无条件终止所有其他工具。**

例如：

```text
read_file(main.py)
read_file(utils.py)
search_code("calculate_total")
```

如果三个操作互不依赖、工作区读取具有足够的一致性要求，并且都已启动并行执行，某个读取失败不代表其他结果必须被丢弃。

相反：

```text
replace_text(main.py)
      ↓
run_test()
```

测试依赖修改成功，失败后应该停止后续依赖步骤。

因此我们应该根据明确的依赖关系判断，而不是使用“所有 Tool 遇到错误一律全部中止”这一粗糙规则。

## 7. 并行的只读操作为什么通常更快？

假设三个操作各自需要一些 I/O 等待：

```text
串行：
read_file A → read_file B → search_code C

并行：
          ┌→ read_file A ─┐
          ├→ read_file B ─┤
          └→ search_code C┘
```

如果彼此无依赖，执行环境允许并行，通常可以减少总体等待时间。

但“只读操作可以并行”不等于“无条件保证同样结果”。还有两个问题：

1. 外部进程可能在读取期间修改文件，因此三次读取未必来自完全一致的仓库版本。
2. 完成顺序不稳定，因此结果必须由调用 ID 对应，不能把“先返回”当成“第一个请求”。

在需要快照一致性的场景里，要增加工作区版本控制或读取一致性机制；V1 可以先在受控练习工作区中约定没有并发外部写入。

## 8. 为什么有依赖的操作通常更适合分轮？

如果模型想：

```text
先读 main.py
→ 再根据内容修改
→ 再运行测试
```

其中后面的参数依赖前面的真实结果。此时一次性生成所有工具参数，不一定可靠，因为模型还没看到最新文件内容或修改执行结果。

通常更自然：

```text
LLM 提议 read_file
   ↓
Tool 返回真实代码
   ↓
LLM 提议 replace_text
   ↓
审批 + Tool 返回真实写入结果
   ↓
LLM 提议 run_test（或由明确 Workflow 强制）
```

这也就是我们早期所说的：

> **没有依赖的 Tool Calls 可以同批并行；有依赖的动作通常需要 LLM→Tool→LLM→Tool 的循环，或者由明确的串行工作流控制。**

## 9. 如何实现受控批次执行器？

我们不会在第一版里直接假设默认 ToolNode 实现了这些业务规则。

可以抽象成：

```python
def execute_batch(calls, approvals):
    # 仅为思路伪代码，不是可运行实现
    # 1. 固定并验证待执行请求
    # 2. 对每个 Tool 做权限与参数检查
    # 3. 已明确独立的只读调用可以并行
    # 4. 存在依赖的调用按次序运行
    # 5. 失败后跳过依赖它的后续调用
    # 6. 为每个 Tool Call 生成对应真实/未执行结果
    ...
```

为什么这里只给伪代码？

因为在编写真正实现之前，还要先回答：

- 谁负责表达依赖关系？
- 一个批次是否允许部分成功？
- 批次中的操作是否必须能回滚？
- 中断后恢复时，如何避免把已经执行成功的写操作再次执行？
- 并发读取期间，工作区版本发生变化时如何处理？

如果这些没定义清楚，直接写一个漂亮的 `asyncio.gather` 只是掩盖了设计问题。

## 10. 一个重要提醒：这不是数据库事务

整批审批的“一批”，**不等于原子事务**。

如果执行顺序是：

```text
读取成功
写入成功
测试失败
```

前面的文件修改不会因为测试失败自动回滚。

同样，如果批次中两次写入，第一次成功、第二次失败，也不能假装“整批都没执行”。

所以最终报告必须如实记录实际发生的副作用。若将来业务要求“要么全部修改，要么完全不修改”，需要单独设计更复杂的事务化或回滚策略，不是批量审批天然附带的功能。

## 11. 本课复盘

现在我们有了 V1 的明确执行原则：

| 情况 | 选择 |
|---|---|
| 本批包含任何受控写操作 | 整批先审批 |
| 本批审批被拒绝 | 全部不执行，分别给出未执行结果 |
| 批次获批 | 只执行获批的具体参数，不重新生成替换 |
| 有依赖的前置操作失败 | 后续依赖调用跳过 |
| 无依赖只读操作 | 可并行，正确按 ID 配对结果 |
| 工具真实失败 | 如实记录，不能伪造成功 |
| 部分写入后测试失败 | 不自动假设文件被回滚 |
| 代码有新修改 | 旧测试通过状态需要失效并重新验证 |

这张表里的规则都不是要求 LLM 自觉记住就能保证的；它们需要 Harness / 工具执行器落实。
