# N00｜我们究竟在学什么：从 LangGraph 到 Coding Agent

> 这一课不要求写代码。目标是先建立清晰的分层模型，知道之后每个知识点要解决什么问题。

## 0. 你并不是来学习一组孤立的 API

假设有这样一个需求：

> “仓库里用户积分的计算不对。帮我找到问题、修复它，并运行测试。修改文件之前需要我确认。”

一个普通聊天模型能给出建议，但不能因此得出“代码已修好”。要让它完成这件事，至少有六类问题：

1. **理解问题**：用户说的“积分”具体对应哪个文件、哪个函数？
2. **获取信息**：如何列目录、搜索代码、读取必要的文件片段？
3. **产生动作**：如何把“我想修改 main.py”变成具体工具调用？
4. **控制风险**：用户不同意，或模型想修改工作区之外的文件，怎么办？
5. **验证结果**：修改真的成功了吗？pytest 是 PASS、FAIL 还是 timeout？
6. **管理流程**：失败之后是否应该重试，如何防止无限循环，何时能报告成功？

只有第一类适合直接交给模型自由分析。其他问题的部分内容需要通过工具和确定性的程序解决。

我们会把这些问题拆开，而不是一开始复制几百行“完整 Agent”代码。

## 1. 先建立六层心智模型

```text
                         用户提出任务
                              │
                    Runner / 交互入口
                     展示进度、审批、恢复
                              │
                      Graph / Harness
                 决定流程、安全策略、完成条件
                              │
                          LLM（模型）
                   理解问题、计划、选择动作
                              │
                      Tool Calling（意图）
                   模型提出要执行的动作
                              │
                        Tools（真实动作）
             搜索、读取、修改、运行测试并返回事实
```

旁边还有三类重要支撑：

- **State（状态）**：程序跨步骤保存的结构化信息，例如已经失败几次、真实测试是否通过。
- **Checkpoint（检查点）**：保存当前任务现场，使中断后可以恢复。
- **Context Builder（上下文构造）**：决定下一次模型调用时，模型应该看到哪些消息与代码片段。

这些层不是严格的部署层级，也不是一层只对应一个类。它们是**职责划分**。

## 2. LLM、Tool、State、Graph 分别回答什么问题？

把下面四句话记住，后面 60 多课会不断用它们检查架构。

### LLM：我认为应该做什么？

例如：

```text
发现测试中 calculate_total 断言失败
→ 我应该搜索 calculate_total
→ 阅读其实现
→ 提出修复方案
```

这是推理和选择。但“提出”不等于“完成”。

### Tool：环境里真正发生了什么？

例如：

```text
read_file("src/calc.py") → 返回真实代码
replace_text(...)      → 返回实际是否修改成功
run_test()             → 返回退出码、输出、超时信息
```

Tool 不应该伪造结果。执行失败、被拒绝、没运行，都不能装作成功。

### State：哪些事实下一步必须可靠地知道？

```python
retry_count = 2
test_passed = False
last_error_type = "TEST_FAIL"
```

如果“普通测试失败最多 3 次”是系统要求，那么计数应由程序维护，而不能让模型从历史文字中猜。

但 State **不是把一切历史和临时信息都塞进去**。比如某次搜索返回的几十行代码，未必需要成为单独的永久字段。

### Graph / Harness：什么事情必须被保证？

例如：

- 修改文件之前有明确批准。
- 测试没有真实通过，不能以 SUCCESS 结束。
- pytest timeout 与测试断言失败走不同处理。
- 普通失败超过次数阈值后停止自动尝试。
- 用户拒绝的操作不能偷偷执行。

这类规则不能仅靠 Prompt 里的一句话来承担。

## 3. “只写 Prompt”为什么不够？

看下面这个 Prompt：

```text
你是严谨的 Coding Agent。
请在修改前获得审批。
如果测试失败，最多重试三次。
测试通过后才能汇报成功。
```

这是非常有用的行为指导，但有明显局限。

**问题一：模型有时会忘记。** 长任务里充满 ToolMessage、代码和日志，模型不一定始终正确统计。

**问题二：模型的文字不是环境事实。** 即使模型回答“测试全部通过”，如果从未执行测试，系统就不能认为成功。

**问题三：权限不是由愿望保证的。** Tool 如果具备直接删除工作目录外文件的能力，即使 Prompt 写了“不要”，代码层仍缺少强制限制。

我们不会因此抛弃 Prompt；它负责软性的行为偏好和推理指导。真正需要可靠执行的规则，下沉到 Tool、Graph、Runner 等程序中。

> **Harness（运行控制框架）不是一个固定 API，也不是 LLM 本身；它是围绕模型组织执行、状态、权限、上下文与验证的一整套工程机制。**

## 4. LangChain 和 LangGraph 的关系

初学者常问：“我已经要学 LangGraph 了，为什么还要 LangChain？”

因为实践中经常这样分工：

| 能力 | 常用组件 |
|---|---|
| 调用聊天模型 | LangChain 的 Chat Model 适配层，如 `ChatOpenAI` |
| 构造模型对话 | `HumanMessage` / `AIMessage` / `ToolMessage` |
| 定义 Tool | `@tool` / `bind_tools` |
| 将流程连接成图 | LangGraph 的 `StateGraph` |
| 让图根据状态分支 | `add_conditional_edges` |
| 保存与恢复工作流 | Checkpointer 与 `interrupt` |

因此学习路线是：**最小 LangChain → 基础 LangGraph → Tool Calling → Agent Loop → 可靠 Harness**。

我们不会先花很多时间研究 LangChain 全部抽象，也不会跳过必要基础直接复制一个复杂模板。

## 5. 本课程与“Python 入门课”有什么不同？

你不必先学习完整 Python 语法。看到这些语言结构要能理解就够了：

```python
class AgentState(TypedDict):
    retry_count: int
    test_passed: bool

def check(state):
    return {"test_passed": True}
```

暂时只记住：

- `TypedDict` 主要提供字典结构与类型提示，并不会自动给字段赋初值。
- `def` 定义函数。
- `state["retry_count"]` 从字典读取字段。
- Node 返回 `{"test_passed": True}`，通常代表**局部更新**，而不是重新构造整个 State。

碰到看不懂的 Python 语法，可以查一下；但这门课始终围绕 Agent 架构组织知识。

## 6. 我们怎么判断自己是真的学会了？

仅仅运行出一次 `print(response)` 不算学会。

例如学习 `ToolNode` 后，你至少要回答：

- 模型把工具名写在自然语言里，和 `AIMessage.tool_calls` 有什么区别？
- `ToolNode` 是什么时候真正执行工具的？
- 一次 AIMessage 有三个 Tool Calls，应该如何对应三个 ToolMessage？
- 如果工具被审批拒绝，应该如何表示“未执行”？
- 为什么一个 Tool 失败不一定等于 Graph Runtime 异常？

我们只在关键章节安排这样的问题；不会每讲一个函数就强行布置练习。毕业项目则会让你自己做职责划分和方案权衡。

## 7. 出错时应该怎样分析？

把错误先归类。不要一看到 traceback 就开始盲目改 Prompt。

| 现象 | 优先排查 |
|---|---|
| `ModuleNotFoundError` | 解释器与依赖装在哪个环境 |
| `KeyError: 'DEEPSEEK_API_KEY'` | 环境变量是否设置、IDE 是否读取到 |
| `KeyError: 'check_count'` | State 初值或上游 Node 更新 |
| `compiled` / `compile` 混淆 | API 名称是否正确 |
| 把 `route_article()` 传给路由注册方法 | 需要函数对象还是调用结果 |
| tool call 格式不被接受 | 是否缺少对应 ToolMessage、ID 是否匹配 |
| Graph 无法从 `interrupt` 继续 | 是否使用 Checkpointer、正确 thread_id、resume |
| 模型称成功但测试 FAIL | 完成条件是否过度依赖模型文字 |

这张表不是所有错误的全集，但它能让我们从“盲猜”变成“分层定位”。

## 8. 最终为什么要做 Coding Agent？

最终大作业不是让 AI 按答案帮你写一个项目就算通过。我们要训练的是：

1. 把自然语言需求转换为可验证的不变量。
2. 判断每个功能属于 LLM、Tool、State、Graph 还是 Runner。
3. 设计必要的工具边界和审批策略。
4. 对普通测试失败、超时、拒绝、工具异常进行不同处理。
5. 判断哪些信息进入 Context，哪些需要重新从真实仓库读取。
6. 能审查 AI 生成的实现，找出潜在绕过边界的路径。

在这个目标下，**写代码可以借助 AI，但架构判断不能完全外包给 AI**。

### 理解检查

试着回答，不必写代码：

> LLM 回答“我已经把 main.py 修好了”，但 `replace_text` 因为旧文本不匹配而失败。此时谁应该产生“是否修改成功”的事实？State 什么时候才可以记录“已修改”？

参考思路：模型只是提出了意图，Tool 的真实执行结果才是依据；Graph 需要的结构化事实应在获得可核验结果之后更新。
